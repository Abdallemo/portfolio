### The Origin Story
This is the frontend companion to **go-route-gen**. While the Go CLI handles the extraction, this package provides the actual developer experience (DX) in the frontend. I wanted to build a client that feels as natural as tRPC but works with a standard Go backend.

### The Problem vs. Solution
**The Problem**: Consuming a REST API in TypeScript usually involves a lot of "manual typing"—manually defining interfaces for each endpoint and hoping they don't break.

**The Solution**: A generic-first Axios wrapper. It takes the route definitions generated by the CLI and uses TypeScript's template literal types to enforce the exact `METHOD /path` strings.

### Deep Tech Specs
- **Strict Mode vs. Loose Mode**: By default, the client is in **Strict Mode**, meaning it will only allow strings that exist in your `API_ROUTES`. If you need to hit external endpoints, you can switch to **Loose Mode**.
- **Global Lifecycle Hooks**: Centralized `onError` and `onUnauthorized` handling directly in the client configuration.

### The "Clever" Logic: Type-Safe Requests
The core power lies in how we validate path parameters. If the Go route is `DELETE /customer/{id}`, TypeScript *requires* the second argument to be an object with an `id`.

```typescript
// Type-Safe Request in @abdallemo/routegen-client
import { GoApiClient } from '@abdallemo/routegen-client'
import { API_ROUTES } from './route' // Generated by go-route-gen CLI

export const api = new GoApiClient<typeof API_ROUTES>({
  baseURL: 'http://localhost:8080'
})

// TS requires 'id' because it's detected in the route string
await api.expect<void>().request('DELETE /customer/{id}', { id: 101 })
```

### Lessons Learned
Building a generic-heavy library taught me a lot about the limits of the TypeScript compiler. I had to learn how to use `infer` and recursive types to correctly parse route strings at compile time.
